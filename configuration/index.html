Configuration reference

facetshot reads facetshot.config.ts (or .mjs, .js), looking upwards from the folder you run it in. Without one, it still works with full URLs and the built-in devices and variants.

defineConfig only gives you types and autocompletion; the file is plain TypeScript, so you can compute values, read environment variables or import helpers.

How the config is checked

Section titled “How the config is checked”

defineConfig returns your object unchanged, and the types are checked only by your editor or tsc, when facetshot is installed in the project. When facetshot loads the config it checks that the file runs and has a default export. It doesn’t check the keys against a schema, so a misspelt key is ignored without a word. Values are checked when they are used: a device, variant, group, profile or persona that doesn’t exist, or a device without a platform and size, stops the run with exit code 2 and says what to fix.

Paths are relative to the config file. Commands run in a shell, from their cwd (relative to the config) or the config’s folder. Commands and environment values can use placeholders such as {port} and {services.api.url}; Placeholders lists them and when each one is available.

Settings that differ per checkout or per person

Section titled “Settings that differ per checkout or per person”

The config is code, so it can read environment variables. It is always evaluated with the environment of whoever asked for the screenshots, even when the background helper runs it, so a teammate or an agent can choose another database or server without editing the file:

Commands and apps facetshot starts (builds, servers, Electron, Mac and Tauri apps) don’t inherit that environment: they get the background helper’s own environment plus their env. The helper’s own environment is that of whatever started it first (your terminal, or an agent’s MCP server). Read a variable in the config and pass it in env when a command needs it. This section is the one place that describes it; other pages link here.

When several checkouts of one project take screenshots at once (agents in separate git worktrees, say), give each its own ports with stablePorts. Each checkout gets a block of ports the first time and keeps it from then on, which helps when a port ends up inside a build (an API address in the web bundle). A removed checkout gives its block back. Blocks come from 5400–5999 unless you pass { from, to }, and are kept in ~/.facetshot/ports.json.

A complete example uses these ports for a web app and its API.

With stablePorts, checkouts never share or stop each other’s servers. Runs from the same checkout share one set, through the background helper.

Build steps

Section titled “Build steps”

web.build, desktop.build, apple.ios.build and the others are build steps:

Field Default
cmd required the command, run in a shell
inputs required files and folders whose contents decide whether a rebuild is needed
output what the build makes; if it is missing, the build runs again
cwd the config’s folder the folder to run it in
env environment for the command
heavy false a heavy build (Xcode, a large bundle): only one heavy build runs on the machine at a time

devices

Section titled “devices”

Each key is a device name. Start from a built-in device with extends, or define one from scratch:

Field For Default
platform all required, unless extends web, ios or window
width, height all required, unless extends size in CSS pixels or points
scale all 2 pixel density
mobile, touch, userAgent web off, off, the browser’s phone browser behaviour
model ios simulator device type, as Xcode names it
orientation ios portrait portrait or landscape
split ios width as a fraction of the screen, for Split View (the app is told the width)
idiom, safeArea ios, snapshots the device family (phone, pad, mac) and screen insets a snapshot renderer assumes
label all the device’s name a friendlier name
extends all a built-in device to start from; the other fields change it
browser web web.browser the browser for this device: chromium, webkit, firefox, chrome, msedge, moz-firefox

variants

Section titled “variants”

Each key is a variant name; each field is one axis. Unset fields keep the platform’s default.

Field Default Values
appearance the platform’s light, dark
text default default, large, xlarge, xxl
contrast the platform’s more, forced
motion reduce on web pages reduce, full
locale the platform’s a BCP 47 tag, e.g. de-DE
timezone the platform’s an IANA zone, e.g. Asia/Seoul
direction the platform’s ltr, rtl
persona web.persona a name from web.personas
network online offline
media screen print

web

Section titled “web”
Key Default
baseURL where your app runs, if you start it yourself
build a build step that runs when its inputs change
serve the server for the app, with the same fields as a service. Leave it out when build.output is a folder of static files (a single-page app, Flutter’s build/web): facetshot serves it, with index.html for paths that aren’t files
browser chromium the default browser: chromium, webkit, firefox, chrome, msedge, moz-firefox
personas, persona nobody signed in who is signed in (below)
storage localStorage entries set before the page loads
ready (below) when a page counts as ready (web.ready)
block URL globs to abort
rewrite [{ from, to }]: URL prefixes to send elsewhere
mask selectors painted over in screenshots
css CSS added to every page
textSizes 125%, 150%, 200% root font sizes for large, xlarge, xxl
clock the real time freeze the page’s clock at this time (ISO 8601)
fullPage false take the whole page instead of the screen

web.ready

Section titled “web.ready”

What each field means, and how route rules work, is in When a page counts as ready.

Field Default
idle 300 milliseconds with no request in flight; 0 doesn’t wait for the network
visible selectors that must be visible
gone selectors that must not be visible
when a JavaScript expression, run in the page, that must be true
timeout 15 000 milliseconds before the screenshot is taken anyway. A session waits at most 8 000 after each step
routes { pattern: rule }: rules with the fields above for some paths, laid over the general ones

Two numbers are fixed: the page is checked every 50 ms, and a request open for more than 10 seconds (long polling) stops counting as in flight.

web.personas

Section titled “web.personas”

Each key names a persona. See Personas for how each field behaves.

Field Default
cookies [{ name, value, domain?, path? }]; domain defaults to the app’s host name, path to /
headers request headers sent with every request, including requests to other sites
storage localStorage entries
storageState a Playwright storage state file; used instead of login when both are given
login a flow that signs in; its result is saved in .facetshot/auth/
ttl 720 minutes a login result is reused

Steps in a persona’s login flow hold their text as written; see Steps.

services

Section titled “services”

Each key names a service; see Services. web.serve takes the same fields.

Field Default
cmd required the command that starts it, run in a shell
cwd, env the config’s folder, none where it runs, and its environment
port auto a number, or auto for a free one
health the service’s own address a path or URL that answers once it’s ready
reuse if this URL answers already, use it and start nothing
startTimeout 120 000 milliseconds to wait for health before the run stops

“Answers” means any HTTP status below 500, within 2 seconds; redirects aren’t followed. While a service starts, health is asked every 300 ms.

limits

Section titled “limits”
Field Default
webPages 4 browser pages being worked at once, across all web devices; never more than 4
simulators 2 simulators booted at once; never more than 2
maxLoad 3 with --no-daemon only: above this many times the core count (1-minute load average), work goes one at a time
lockDir ~/.facetshot/locks where machine-wide locks live
lockNames { build: 'build.lock', macWindow: 'mac-window.lock' } lock names, to share locks with your own scripts

A project can lower these limits for itself but not raise them. How they are shared across runs, and the load brake (work slows down when the machine is busy), are described in Shared limits.

Locks are folders created with mkdir, so shell scripts can take the same ones: mkdir build.lock before a build, rmdir build.lock after. Point lockDir and lockNames at the locks your team’s scripts already use, and facetshot takes its turn with them. Heavy builds share the build lock, so only one runs at a time.
