Sign-in, servers and test data

To log in to your app before each screenshot, start the servers it talks to, or make records for it to show, add these parts to facetshot.config.ts:

Part What it does
Personas sign in as a user, with cookies, headers, storage or a login flow
Services start your API, a mock server or anything else your app talks to
Test data make the records a page needs before the first screenshot, and remove them afterwards

The page ends with a complete example of a web app with its own API. How facetshot builds and serves the web app itself is in Web apps.

Personas

Section titled “Personas”

A persona is a signed-in user. Define personas under web.personas, choose the usual one with web.persona, and choose another for some screenshots with a variant:

The fields are listed in the configuration reference. A few things to know:

  • cookies go to the app’s own host name unless you give a domain, so an API on another host doesn’t get them. They need a known app address (web.baseURL or web.serve).
  • headers are sent with every request the page makes, including requests to other sites.
  • login is a flow that signs in. It runs once in a fresh browser context, and the signed-in state is saved to .facetshot/auth/<persona>.json and reused until it is older than ttl minutes. If the flow fails, the run says that signing in failed and which step stopped. Its steps hold any password as written, so use a test account, and keep the flow out of git if the password matters.
  • If a persona has both storageState and login, the file is used.
  • Personas apply to web pages and Storybook. Electron windows don’t get them yet (Desktop apps).

Sign-in that only exists in development

Section titled “Sign-in that only exists in development”

Many apps sign in a fake local user only in development mode, so a production build can’t sign in locally. One way around this is a separate build mode for screenshots, which keeps the local sign-in and can’t be deployed:

In your app, enable the local sign-in when import.meta.env.DEV || import.meta.env.MODE === 'screenshots'. Write that condition inline where it is used, since bundlers remove unused code reliably only when the constant is right there. Build that mode without a deployment adapter, so the output can’t be shipped by accident, and add a test that a normal production build doesn’t contain the local user.

Services

Section titled “Services”

An API, a mock server or anything else your app talks to goes under services. Each service starts before the first screenshot and stays up for later runs while the background helper is running:

  • port is a number, or auto for a free one. Leaving it out means auto.
  • health is a path (or full URL) that answers once the service is ready. facetshot waits up to startTimeout milliseconds for it. What counts as an answer, and the defaults, are in the configuration reference.
  • reuse: if this URL already answers, facetshot uses it and starts nothing. The URL itself is asked, not health, so give one that answers only when the service is up (for example http://localhost:4000/health).
  • If the port is taken by something that doesn’t answer health, the run stops and the message shows how to find that process.
  • Services start one after another, in the order you list them, so a later service can use an earlier one’s {services.<name>.url}.

Placeholders

Section titled “Placeholders”

Commands, environment values and targets can contain placeholders, which facetshot fills in once the value is known. Each one is available only from the moment it exists:

Placeholder Is Can be used in
{port}, {url} the port of this service or server, and http://localhost:{port} that service’s or server’s own cmd and env
{services.<name>.url} a service’s address later services, builds, the web app’s serve, app env, targets
a name fixtures.setup returns e.g. {project} builds, servers, app env, targets
{web.url} where the web app is served targets and flow addresses only

{web.url} is set only after the web app’s server is up, which is after services and test data have been made. It can’t be used in a service’s env (to tell an API which origin to accept, say). Give the web app a fixed port instead, as in the complete example.

Test data

Section titled “Test data”

Pages that show a specific record need one to exist. fixtures.setup is a function that makes test data before the first screenshot and returns string values for {placeholders} in targets. fixtures.remove deletes one thing it made:

setup receives a context with these fields:

Field What it is
ctx.runId the run’s id
ctx.label facetshot-<run id>. Put it on what you make, so it is easy to find
ctx.services each service’s address: ctx.services.api.url
ctx.record(kind, id, extra?) writes the item to a ledger in .facetshot/ before you return. If the run is killed, the next run removes everything the ledger lists
ctx.log(message) a line in the run’s output

remove receives { kind, id, extra } as recorded, and the same context.

While the background helper is running, test data is made once, reused by later runs, and removed when the helper stops. Set reuse: false to make fresh data for every run and remove it when that run ends.
