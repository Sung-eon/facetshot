Logs

A screenshot shows what a screen looks like; its log shows what happened while it was on screen. facetshot keeps both, side by side, for every screenshot of a web page, a Storybook story, a desktop app or an iOS app, and for every session.

What’s recorded

Section titled “What’s recorded”
Source What
console everything the page logs, at its own level (console.error is an error, and so on)
page uncaught errors, with where they were thrown, and crashes
navigation each address the page goes to
network each request with its status and time; 4xx is a warning, 5xx and failures are errors
dialog alerts, confirms and prompts, with their text
main an Electron app’s main process: its console output, standard output and error
app a Mac or Tauri app’s standard output (info) and standard error (warn)
os_log an app’s lines in the system log; os_log:<category> when they have a subsystem
server:name new lines in the logs of the servers and builds facetshot started (.facetshot/logs/)

Requests for scripts, styles, images and fonts are kept at the debug level, so they don’t crowd out the requests your app makes on purpose. A page keeps its last 5,000 entries, so a page left open for hours can’t use more and more memory.

In a run

Section titled “In a run”

Every run writes its logs next to the screenshots, in two files:

  • logs.txt, for people: a section per screenshot with times from when the page was opened, and the servers’ output at the end. Debug lines are left out and counted.
  • logs.ndjson, for programs and agents: one JSON object per line, debug lines included.

The summary ends with a line pointing at them (Logs: … (23 lines; 1 warning)). report.html shows them folded at the end, with a badge on each screenshot that logged errors. The manifest has logs for the run and log (counts) for each screenshot.

To read them again later:

Agents get a screenshot’s log lines with inspect, next to the screenshot itself.

Logs and checks

Section titled “Logs and checks”

The console and network checks turn console errors and failed requests into findings in the run’s summary. Logs are the full record behind them. Use the checks to know that something went wrong, and the logs to see what happened around it.

Masking

Section titled “Masking”

Tokens, keys, passwords and similar values in log lines are masked before they are written to logs.txt and logs.ndjson. The raw server logs in .facetshot/logs/ are not masked. Security lists exactly what is and isn’t masked.

Apps outside the browser

Section titled “Apps outside the browser”
App What is recorded
Electron the window as a web page, plus the main process: its console messages with their level, and what it writes to standard output (info) and standard error (warn). A line that reaches both is kept once.
Native Mac apps, Tauri’s real window what the app writes to standard output (info) and standard error (warn), and its lines in the system log (Logger, os_log, NSLog)
iOS simulator the app’s lines in the system log (Logger, os_log, NSLog). Swift’s print doesn’t reach facetshot from a simulator.

From the system log, only lines sent by code in the app’s own bundle, or under a subsystem that isn’t Apple’s, are kept: Apple’s frameworks write a lot in an app’s process, and little of it is about the app. Two limits come from the system log itself: Logger.debug lines aren’t kept (facetshot reads the log at the info level), and values in a message show as <private> unless the app marks them .public (\(name, privacy: .public)).

On a Mac, facetshot launches the app with NSUnbufferedIO=YES (as Xcode does), so Swift’s print reaches the log as it happens rather than when the app quits.
